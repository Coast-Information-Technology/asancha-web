Step 4 — verification_documents
Purpose: collect evidence needed to verify the Property Owner Business Profile/person/company.

Endpoint:
PUT /onboarding/me/property_owner/steps/verification_documents

This step changed significantly.

All ordinary Business Profile onboarding flows now use verification_documents, and Property Owner onboarding must not collect Property-specific evidence in this step.    Pasted text(20261027-054602)

The exact required document keys are intended to be driven by a backend requirement definition containing:
- field key
- Document type
- required/optional/conditional status
- condition
- evidence subject
- applicability.    Pasted text(20261027-054602)
For Property Owner, the logical requirement matrix should be:
Evidence field/category	Required?	Type	Description
identity Document public ID	Required/conditional by requirement definition	string	References a canonical identity Document owned by the user/profile.
proof-of-address Document public ID	Conditional	string	Required where address verification applies.
authority-to-represent Document public ID	Conditional	string	Required when the Property Owner is acting as an authorised representative rather than directly as owner.
executor/legal-authority evidence public ID	Conditional	string	Required where ownershipCapacity = executor or equivalent.
company-registration Document public ID	Conditional	string	Required when operatingMode = on_behalf_of_company.
company/business evidence public ID	Conditional	string	Additional Company-subject evidence where the requirement definition demands it.


The onboarding rules support identity, proof of address, authority evidence, Company ownership evidence, executor/legal authority evidence and ownership-related evidence conceptually. Asancha Onboarding Rules

However, after the later standardization, Property-specific ownership evidence belongs to Property Submission, not Property Owner profile verification. Therefore we should not reintroduce the old proofOfOwnershipDocumentPublicId here merely because it appeared in the legacy step.

Important policy architecture point
acceptedPolicies in an onboarding step should not become the authoritative policy acceptance record by itself.

Canonical policy acceptance belongs to the versioned policy_acceptances mechanism. The onboarding rules explicitly require acceptance to be stored there. Asancha Onboarding Rules

So structurally I would regard acceptedPolicies here as an acknowledgement/summary field only if the deployed contract still requires it. The actual policy acceptance authority remains the Policy domain.
